## What failed, and why

V0R4 terminated `BLOCK_RUNTIME_IDENTITY` with `DSH_HOME is missing the Stage-A
package scope`. The composite qualification had always constructed its DSH_HOME
through a qualification-only helper, `prepareDisposableDshHome`, which copied
profile bytes and linked packages out of an ambient scratch directory at
`/home/swirky/DevHub/scratch/qntylab-dsh-v1r3r1-repair/dsh-home`. The live path
had no equivalent step, so it inherited that ambient directory as an unverified
precondition. Classification: `QUALIFICATION_TO_ACTION_TIME_DSH_HOME_MATERIALIZATION_GAP`.

The ambient directory was not repaired. It remains byte-for-byte untouched as
the physical referent of the immutable V0R4 evidence, and negative control
NC-16 re-executes the original failure against it to prove it still cannot
substitute for a materialized home.

## M-01 boundary decision

`MATERIALIZATION_BY_CANONICAL_COPY_AND_IDENTITY_BOUND_SYMLINK_ONLY` — the
authorization's option C alone. **No package manager was invoked** and no

## Canonical provenance

Every materialized object derives from a Git-bound or contract-bound source.

**Headless profile bytes.** All four files are generated byte-exactly from
template constants in the pinned DSH source at commit
`99f6f02fecdb7dff40c3fbc9470f5907c29f74ca`:

| file | pinned source | constant |
| --- | --- | --- |
| `cordis.yml` | `apps/cli/src/profile-boot.ts` | `PROFILE_ROOT_CONFIG` |
| `cordis.patch.yml` | `packages/boot/app-boot/src/profile.ts` | `PROFILE_PATCH_TEMPLATE` |
| `pnpm-workspace.yaml` | `packages/boot/app-boot/src/profile.ts` | `PROFILE_PNPM_WORKSPACE` |
| `package.json` | `packages/boot/app-boot/src/profile.ts` | `initProfile` + `SHIPPED_PROFILE_TEMPLATES.headless` |

Both source files are byte-identical to the pinned Git HEAD. The four derived
digests equal the qualified contract's `qualifiedDshHomeProfileDigests`, so the
ambient copy is confirmed as a *consequence* of the canonical source rather than
a source of authority.

**Package graph.** Derived, not copied. The materializer reproduces DSH's own
`healProfilesModuleFallback` algorithm — a BFS over `dependencies` and
`peerDependencies` from the installation anchor `apps/cli/package.json`, first
resolution winning — which is the pinned runtime's own definition of the flat
profile module fallback. To that closure it adds the six Stage-A runtime
packages pinned by the qualified contract, two of which (`dsh-subagent-codex`,
`dsh-subagent-claude-code`) are out-of-tree plugins the closure does not reach.

Result: 251 packages, 255 manifest objects, **every symlink target
resolving inside the pinned runtime root and zero escapes**. The old ambient
tree had the same 247-entry closure but anchored in scratch, plus five stale
entries including three that escaped into the operator home.

The BFS skips declared-but-uninstalled dependency edges, exactly as DSH's own
heal does. That skip is not silent: all 88 skipped names are enumerated in the
manifest at `provenance.skippedDependencyEdges`, with
`loaderVisibleUnresolvedPackages: 0`. None is reachable through the flat
fallback, and a real DSH boot over a materialized home adds zero links — which
is the strongest available evidence that the closure reproduction is exact.

**`@img/colour`.** The authorization flagged it as possibly missing from the
pinned store. Both halves of that risk are resolved: it *is* present in the
pinned store at `@img+colour@1.1.0`, and it is *not* required in the flat
fallback — it resolves from `sharp`'s own real directory through ordinary Node
resolution. It is therefore not materialized, and no `SOURCE_CONFLICT` arises.

## Hostile review

One independent hostile review attacked the eighteen required vectors; fifteen
held on first contact. It returned 1 High, 3 Medium and 2 Low, all now repaired
— see `hostile_review.md`.

The High was real and worth the phase: `verifyHomeManifest` took its
symlink-containment root from the manifest it was verifying, and that field sits
outside the identity digest. The reviewer executed the bypass, forging a home
with the root widened to `/` and a package symlink repointed at attacker code,
and it passed. The root now comes from the pinned runtime manifest and the
recorded value is checked as a claim rather than trusted as authority. Two
supplementary controls, NC-19b and NC-19c, reproduce that forgery and the
related addition-blindness and require both to block. The twenty required
controls remain exactly the twenty the authorization enumerates.

A targeted re-review covering only the repaired surface returned
`PASS_NO_CRITICAL_HIGH`.
